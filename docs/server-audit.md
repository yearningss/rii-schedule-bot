# Аудит серверной логики РИИ Расписание

Дата: 2 октября 2026 года. Ветка: `design/material-3-redesign`.

Проверены клиент сайта института, HTTP-обработчики, SQLite/SQLAlchemy, фоновая отправка уведомлений, агрегация табло и расписаний преподавателей, справочник преподавателей, сезонные темы и обработчики Telegram. Исправления относятся к исходному коду ветки; рабочий сервер не обновлялся. Доступа к его журналам, прокси, CPU, диску и базе пользователей не было. Поэтому ниже разделены подтверждённые дефекты кода и оставшиеся направления проверки.

## Что вызывало лишние ожидания и исправлено

| Проблема | Последствие | Изменение |
|---|---|---|
| Кэш расписаний и групп не объединял одновременные загрузки | При истечении кэша несколько клиентов одновременно обращались к одному источнику. Табло, преподаватели и уведомления дополнительно умножали запросы | Добавлен `SingleFlight`: одна загрузка на ресурс, остальные ждут её результат. Отмена одного клиента не отменяет общую загрузку |
| Одновременная сборка одинакового табло | Несколько экранов повторно агрегировали все группы | Сборка табло тоже объединяется |
| Срок кэша отсчитывался от начала запроса, через системные часы | Медленная загрузка сокращала полезное время кэша; перевод часов нарушал срок действия | Используются монотонные часы и момент успешного завершения |
| Пустой список групп не считался закэшированным | Повторные запросы даже после корректного пустого ответа | Проверяется наличие результата, а не его непустота |
| Погода и GitHub после ошибки запрашивались снова при каждом обращении | До 4 и 5 секунд ожидания соответственно, повторяющиеся подключения | Объединение загрузок и пауза 60 секунд после неудачи; ранее полученный результат сохраняется |
| Погода загружалась после всех расписаний табло | Время двух внешних операций складывалось | Погода загружается параллельно расписаниям |
| Расписания для уведомлений загружались последовательно | Одна медленная группа задерживала все последующие | Параллельная загрузка с обработкой ошибки каждой группы отдельно |
| Проверка изменений и напоминания работали в одном цикле | Проверка десятков групп и рассылка изменений задерживали напоминания | Независимые фоновые циклы с корректной отменой при остановке |
| `/group` всегда обходил кэш списка групп | Лишнее обращение к институту при каждом выборе группы | Используется существующий пятиминутный кэш |
| DISTINCT по идентификатору и названию группы | При разных сохранённых названиях одна группа попадала в проверку изменений несколько раз | Группировка по идентификатору |
| Выборки уведомлений по группе без подходящего составного индекса | Рост стоимости запросов при увеличении базы | Добавлен индекс `(group_id, notifications_enabled, notify_changes)` через повторяемую миграцию |

Параллелизм соединений к сайту института ограничен 12; общий тайм-аут запроса остаётся 15 секунд, соединение — 5 секунд, чтение — 10 секунд. Значение 12 — исходное ограничение нагрузки, а не результат настройки по статистике рабочего сервера. При медленном источнике очередь соединений входит в общий тайм-аут, поэтому часть расписаний большого табло всё ещё может не загрузиться вовремя.

## Другие исправленные баги

- Некорректный `group_id` возвращает HTTP 400 вместо 500.
- Ответ источника без списка групп или объекта расписания не затирает исправный кэш пустым значением.
- Недоступное расписание на табло больше не выдаётся за выходной день.
- При недоступной погоде после запуска не показываются выдуманные `+12°C` и «Ясно».
- Добавлено время седьмой пары по уже имеющемуся регламенту звонков проекта: 18:50–20:20.
- Обычный текст уведомлений отправляется без разбора HTML: символы `<`, `>` и `&` не ломают отправку.
- HTTP-сервер закрывает незавершённые общие загрузки и клиентскую сессию; остановка бота дожидается отмены фоновых задач.
- В журнал добавляется метод, путь и длительность запросов API, занявших от секунды. Строка запроса и токены в эту запись не включаются.
- Уточнены зависимости SQLAlchemy для asyncio и база часовых поясов для Windows.

## Проверки и измерения

17 автоматических проверок прошли локально на Python 3.14. Использовались отдельная временная SQLite-база и локальный HTTP-источник; сообщения реальным пользователям не отправлялись.

Проверены: 50 параллельных запросов одной группы, независимость разных групп, принудительное обновление, сохранность кэша при ошибке, пустой список, семестр строкой, срок кэша после завершения загрузки, отмена одного клиента, повтор после ошибки, пауза при сбое погоды/GitHub, объединение табло, независимость двух циклов уведомлений, неверные идентификаторы, седьмая пара, HTML-символы и повторный запуск миграций.

Сравнение прежнего и нового клиента на одном искусственном источнике: 50 запросов одного расписания, обработка источником по 50 мс, одновременно не более четырёх обработчиков.

| Показатель | Прежний клиент | Новый клиент |
|---|---:|---:|
| Обращения к источнику | 50 | 1 |
| Завершение всей пачки | 0,831 с | 0,057 с |

Это модель очереди внешнего сервера, а не измерение ускорения сайта для всех пользователей. Главное подтверждённое улучшение — устранение 49 дублирующих запросов в этой пачке.

Дополнительно проверен настоящий публичный источник института двумя запросами: 34 группы получены за 0,231 с, одно расписание — за 0,065 с. Повтор расписания из памяти занял около 0,000005 с. Эти результаты показывают работоспособность формата ответа в момент проверки, но не исключают периодических задержек института или проблем рабочего сервера.

Добавлена проверка сервера в GitHub Actions для Python 3.10 и 3.12. Команда локального запуска: `python -m unittest discover -s tests -v`.

## Приоритетные проблемы, оставшиеся в коде

### 1. Критично: сервер не проверяет вход через Яндекс

`services/web_server.py`, `handle_api_app_auth_yandex`: сервер принимает `yandex_id` и профиль от клиента, а при отсутствии идентификатора использует часть присланного токена. Запроса к Яндексу для подтверждения принадлежности токена нет. Следовательно, доверенный токен приложения может быть выдан для неподтверждённой личности. Клиент уже передаёт `access_token`, поэтому исправление должно получать проверенный профиль на сервере и игнорировать присланные клиентом персональные поля.

### 2. Высокий приоритет: операции с пользователем и устройством без проверки владельца

`services/web_server.py`, `handle_api_sync_user`: достаточно прислать `user_id`, чтобы поменять его группу и подгруппу. Подпись Telegram `initData` не проверяется. `handle_api_app_device_unlink` допускает отвязку по `device_id`/`client_user_id` без действующего токена владельца. `database.py` создаёт гостевые токены как `dev_` плюс идентификатор устройства: это производная идентификатора, а не отдельный случайный секрет.

Нужны проверка Telegram-подписи и связка устройства с серверным секретом. Это затрагивает действующие приложения и требует совместимой миграции гостевых устройств. Исправления производительности не закрывают эти проблемы.

### 3. Высокий приоритет: гонки регистрации и подтверждения входа

`database.py`, `register_or_update_device_user`: новый гостевой ID вычисляется через `min(user_id) - 1`. Два одновременных запроса могут выбрать одинаковый ID, а повторная регистрация одного устройства не защищена уникальным ограничением. Возможны ошибки SQLite и HTTP 500.

`confirm_auth_session` сначала читает pending-сессию, затем меняет её статус. Это не атомарное условное подтверждение; при одновременных подтверждениях возможны конкурирующие токены или ошибки записи. Нужно подтвердить сессию условным UPDATE и проверить число изменённых строк.

### 4. Средний приоритет: срок действия и накопление токенов

`get_auth_session` меняет статус истёкшей сессии только если она pending. Подтверждённая сессия продолжает возвращать токен через `/api/app/auth/check` после `expires_at`. Это расширяет время, когда знание старого токена запроса на вход позволяет получить токен аккаунта.

Таблицы сессий и токенов не очищаются по сроку; явного срока действия `AppUser` нет. Нужны ограниченное время получения результата входа, отзыв токенов и фоновая очистка.

### 5. Средний приоритет: уведомления всё ещё могут пропускаться

`services/notifier.py`: событие проверяется точным равенством минуты. Долгая рассылка, пауза процесса или недоступность источника могут пропустить нужную минуту. `_sent_keys` помечается до успешной отправки, а ошибки отправки подавляются; временный сбой или ограничение Telegram не приводит к повтору. После перезапуска процесса ключи теряются и возможны повторы в текущую минуту.

Нужны сохраняемая очередь событий, ограниченные повторы, обработка Telegram RetryAfter и проверка интервала между последними проходами. Независимые циклы уменьшают один источник задержек, но не обеспечивают гарантированную доставку.

### 6. Средний приоритет: первая загрузка всё ещё зависит от всех групп

`services/kiosk_service.py`: табло и расписание преподавателя собираются из расписаний всех групп. При пустом кэше ошибка или задержка одной группы удерживает ответ до её тайм-аута. Кэш живёт только в процессе и исчезает при перезапуске; несколько процессов имеют независимые кэши.

Следующий этап — отдельное обновление снимков в фоне, хранение последнего успешного снимка и явный признак его возраста. При этом уведомления об изменениях должны сравнивать свежие данные, чтобы не объявлять ложные отмены. Добавлять выдачу старого расписания без такой маркировки нельзя.

### 7. Средний приоритет: доступность и защита внешнего источника

`services/api.py`: `ssl=False` отключает проверку сертификата института. Существовавшее поведение сохранено, чтобы не изменить доступность источника без проверки сертификатов с рабочего сервера. Нужна проверка корректной цепочки сертификатов и включение проверки TLS.

Произвольные положительные `group_id` всё ещё принимаются и попадают в словари кэша после успешного ответа. Нет предела числу таких ключей и ограничения частоты запросов. Нужно проверять принадлежность группе, ограничивать кэш и защищать дорогие методы от частых обращений.

### 8. Низкий/средний приоритет: метаданные обновлений и вторичные операции

- `get_app_changelog_data` формирует имена, размеры и ссылки файлов релиза вручную. Если конкретный релиз не содержит такого файла, клиент получает несуществующую ссылку; значение версии при недоступном GitHub также задано в коде. Нужны подтверждённые метаданные релизов.
- `get_teacher_full_schedule` повторно сканирует все занятия при каждом открытии преподавателя. После устранения сетевых дублей можно измерить стоимость и при необходимости построить индекс преподавателей по версии снимка.
- Сохранение аватара и первое чтение справочника преподавателей выполняют файловые операции непосредственно в асинхронных обработчиках. На медленном диске это задерживает другие запросы. Запись аватара стоит вынести в поток и делать атомарно.
- Вход через Telegram сначала загружает фотографию пользователя, затем подтверждает сессию. Медленный Telegram задерживает вход из-за необязательного аватара.
- Некоторые изменения профиля выполняются отдельными транзакциями: при ошибке возможен частично сохранённый профиль.

## Что проверить на рабочем сервере

После развёртывания ветки сравнить время API до и после, число запросов к институту, журналы новых медленных запросов, перезапуски, число процессов и нагрузку SQLite. Отдельно проверить время ответа прокси и доступ к сайту института с самого сервера. Для уверенного вывода о причинах задержек конкретных пользователей нужны эти измерения; локальный тест их не заменяет.
